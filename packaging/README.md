# Releases and the installer

A release is four tarballs, one per target, `SHA256SUMS` and `install.sh`, built by
[.github/workflows/release.yml](../.github/workflows/release.yml) when a `v*` tag is pushed.
Participants install with one command (macOS, Linux, or Windows inside WSL2):

```sh
curl -fsSL https://github.com/agentcommunity/goal-cup-tracer/releases/latest/download/install.sh | sh
```

[install.sh](install.sh) is plain POSIX `sh` and needs no `sudo`. It picks the build for macOS
arm64 or x86_64, or Linux arm64 or x86_64 (WSL2 is Linux), downloads the release's `SHA256SUMS`
and the tarball, refuses the install on a checksum mismatch, runs each new binary from the temporary folder (a
build the machine cannot run, such as one that needs a newer glibc, stops the install with the
old one untouched), and installs into `~/.local`: the
binaries in `bin/`, the connectors in `share/goalcup/`. It edits no shell profile. Options:
`--version <x.y.z>` (after `sh -s --`) installs that release instead of the latest, and `--prefix
<dir>` installs elsewhere. Native Windows gets an `install.ps1` later. The checksum catches a
damaged or truncated download; it comes from the same release as the tarball, so it is not a
signature.

The binaries are unsigned and not notarized. A download by `curl` is not quarantined on macOS, so
Gatekeeper does not stop them. There is no Homebrew tap.

## What a release holds

| Asset | What it is |
|---|---|
| `goalcup-<version>-<target>.tar.gz` | One per target: `aarch64-apple-darwin`, `x86_64-apple-darwin`, `x86_64-unknown-linux-gnu`, `aarch64-unknown-linux-gnu` |
| `SHA256SUMS` | `sha256sum` of each tarball |
| `install.sh` | The installer, copied from [install.sh](install.sh) |

Each tarball unpacks to one directory laid out as an install prefix, so it also runs where it is
unpacked, with no installer:

```text
goalcup-<version>-<target>/
  bin/goalcup  bin/goalcup-daemon  bin/goalcup-verify
  share/goalcup/connectors/     every folder under connectors/, exactly as committed
  LICENSE  NOTICE  THIRD-PARTY-LICENSES.md
```

[scripts/package-release.sh](../scripts/package-release.sh) archives the whole `connectors/` tree
with no list of names, so a merged connector ships by being merged. (The pins are compiled into the
binaries, so a connector merged after a release needs a point release.)

`goalcup` finds the connectors as `<its own directory>/../share/goalcup/connectors`: beside the
path it was started by (`~/.local/bin/goalcup`, which survives upgrades), else beside its resolved
path (`connectors_dir` in `crates/goalcup-cli/src/config.rs`). It starts `goalcup-daemon` from
beside itself, so nothing is configured and nothing is written outside the install.
`THIRD-PARTY-LICENSES.md` holds the licence texts of every crate the binaries link for that
target, generated by [scripts/third-party-licenses.py](../scripts/third-party-licenses.py).

Each target is built with the pinned compiler (`rust-toolchain.toml`, the one the gate uses) on a
runner of its own architecture: Apple silicon, Intel (`macos-15-intel`), x86_64 and arm64 Linux.
There each tarball is unpacked and smoke-tested by
[scripts/smoke-release.sh](../scripts/smoke-release.sh): all three binaries print the release
version, the tarball holds every connector folder of the repository, and `goalcup doctor --json`
from the unpacked tree finds them with every pin passing. Then `install.sh` is piped to `sh`
against that tarball with a scratch `HOME`, and the installed tree must match the repository's
`connectors/`. A failure fails the release. The Linux tarballs are built on Ubuntu 22.04 and need
glibc 2.35 or later (no musl). A built tarball does not mean a capture works on that platform: see
the [README](../README.md#platforms).

## Cutting a release

The version is written in one place: `version` under `[workspace.package]` in `Cargo.toml`. Every
crate inherits it, and the binaries and the report fields (`tracer_version`, `daemon_version`,
`verifier_version`) read it at build time. Docs say "the latest release" and never write it;
`scripts/check-version.py`, run by both gate tiers, fails on any other copy.

The active repository ruleset protects `main`, so `scripts/release.sh` never pushes it: the
version bump is a pull request, and the release is a tag on merged `origin/main`.

For a package build, fetch locked dependencies for the selected target before using offline build
commands. The release workflow fetches its target graph, then builds with `--offline`.

1. If the intended version is not already on `origin/main`, run
   `sh scripts/release.sh prepare <x.y.z>`. It branches `release/v<x.y.z>` from `origin/main`,
   sets the version, updates `Cargo.lock`, checks it, commits, pushes the branch and opens a pull
   request. If `origin/main` already has that version, `prepare` says so and does nothing. Merge a
   version PR through the repository ruleset.
2. Fetch the merged `origin/main` and run `sh scripts/gate.sh full` and the separate
   `sh scripts/linux-check.sh` on that exact versioned commit. Run them sequentially; the Linux
   check needs Docker with privileged-container support. The tag command does not run either check.
3. Run `sh scripts/release.sh tag <x.y.z>`. It fetches, checks that `origin/main` has the version in
   `Cargo.toml`, tags that commit (never a local branch) and pushes only the tag.
4. The tag starts the workflow. It refuses a tag that differs from `Cargo.toml`, builds the four
   targets and creates the GitHub release with every asset.

The installer stages the new binaries and connector tree before changing the prefix and refuses a
directory at a binary destination. If a handled failure or signal occurs during promotion, it
attempts to restore the previous files. If restoration itself fails, it preserves and reports the
recovery paths. This is rollback for handled failures; separate file renames do not make the whole
prefix atomic against power loss, forced process termination, or concurrent installs.

To try the build without releasing, start the workflow by hand (`gh workflow run release.yml --ref
<branch>`, or Actions, `release`, Run workflow). It uploads the tarballs as run artifacts and
publishes nothing, because the publish job runs on a tag push only. Download them with `gh run
download <run-id>`. To try the installer on them, put the tarballs and a `SHA256SUMS` (`shasum -a
256 *.tar.gz`) in one folder and run `GOALCUP_RELEASE_BASE=file://<folder> sh packaging/install.sh`.
