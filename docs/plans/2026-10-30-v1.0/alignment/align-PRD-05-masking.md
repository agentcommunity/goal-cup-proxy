| P05-1 | PRD-05 section 4 "The left guard", escape table row 1 (198), and "One predicate" (222-227) | The guard lets a key through after a backslash escape only when an **odd** run of backslashes comes before the letter. That parity is right for quotes (`\"`, `\\\"`, 1, 3, 7 backslashes) but wrong for letter escapes. A newline in JSON nested inside a JSON string is `\\n` (2 backslashes), and 4 at the next level. Hermes tool results are JSON nested in JSON (`run_secret.rs:25-26` says so), and a tool output wrapped as JSON inside a string field gives the same form. So a key at the start of a line in nested tool output (`\\nsk-…`, `\\nghp_…`) follows `n`, which is glue, after an even run, and is **dropped**. That is not the loss the owner accepted ("a key typed right after a letter or digit"): the key follows a newline. The same applies to `\\u001b` (ANSI) and `\\uXXXX` at the second level. Today's rules (no guard) mask it, so this is a new leak | Point 4; ledger M1 (accepted loss is only "after a letter or digit") | blocker | Row 1: change "an odd run of backslashes, then one letter or digit" to "a run of one or more backslashes, then one letter or digit". Add to the example column `\\nsk-…`, `\\\\nghp_…`. In "Automated tests", `mask_rules.rs` guard cases: add "a key after `\\n` and after `\\\\n` masks". Base64 blobs hold no backslash, so this changes nothing for A2 |
