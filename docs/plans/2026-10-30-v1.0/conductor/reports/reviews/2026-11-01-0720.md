## 6 Risks

1. **Point 4, shape-only masking (high).** New key formats leak until a shape exists, and agents often run `env` or `printenv`, which sends the key in a request body. The Gemini leak is the proof. The root cause is the default "no" on owner question 3 (exact-value masking). Masking the exact values of the key variables the connector already names, read from the harness environment at start, would have caught it with no file read. Raise it again, with this evidence (section 7).
2. **Point 1, history check blind on the main harness (high).** Every Claude Code row warns `history_complete`: "resends answer N (text): text not found in any response" (in every rung and C4 report). That check is the only missed-call detector (ledger T4). If it always warns, a real missed call looks the same. The verify lane found no fault "without the real record"; fetched copies now exist (`c4/out/runs/*/fetched`). Settle it before the `full` rows.
3. **Points 3 and 7, a dead watchdog ends a TUI harness (medium to high).** Rung 5 confirms PRD-02 9.1 on both core harnesses: kill the watchdog and the harness loses its terminal and exits. That holds in the rig's shell, and by PRD-02 9.1 in an interactive shell too. All 15 harnesses are run as TUIs, so for participants R3b ("the harness never restarts") holds only when the terminal outlives `goalcup start`. The real recovery path is then `goalcup continue` (r5b works). Also, once the watchdog is gone, a recorder crash blocks the agent ("your agent cannot reach the model service") until the participant types `goalcup recover`, which may mean hours blocked if they are asleep at hour 100. The participant guide must say both plainly. A structural fix is to invert the process tree, so the harness stays the shell's job and the watchdog runs beside it. That costs the end-screen hand-off and is too large for this build without the owner.
4. **Point 6, what the participant is shown (medium).** After a recover the participant sees no end screen at all (rung 5 F4). Recover's "off from" time can differ from the record's gap by 31 s (rung 5 F5). Startup calls are counted as model requests (Kimi), and OpenCode shows "0 session files". Every Codex run also prints a PROBLEM line asking the participant to record `ab.chatgpt.com` (rung 5 Codex status), which is noise if that host carries no model traffic. C6 compares these counts, so they decide rows too.
5. **Point 5, long-run upload unproven (medium).** Every real run has lasted 3 to 6 minutes. Part rotation at 60 minutes, multi-part upload, the X5 lag bound and pruning have no real run until A1 or A2, which are scheduled last.
6. **Point 2, many subagents unproven (medium).** Rows show one child per run. X2 needs 15 or more, with 10 running at once.
7. **Point 7, harness coverage (medium).** 0 of 15 verified. Rung 1x: only opencode2 and kilo pass at micro. Cline, Crush, Kimi and OpenClaw fail on setup data, and several fixes need owner answers or a core change (OpenClaw workspace in `connector/launch.rs`). Expect 3 to 6 verified at release unless phase 5 starts by Wednesday.
8. **Codex usage depends on native files (low to medium).** Every Codex row has `calls_without_usage` on the wire, with tokens from native only. If Codex's session files change, usage for the main OpenAI harness vanishes.
9. **Process.** Idle owners on live blockers: core (L-R2), PRD-14 (heavy group), PRD-04 (no lane; `SnapshotCursor.fid` and OpenClaw `source_changed` gaps). The night log is stale. Code is about 2.2 times its ceilings, which slows every review.
