### 1.2 OTel GenAI semantic conventions, September 2026

- The conventions moved out of the main semconv repo into `open-telemetry/semantic-conventions-genai`. **Status: Development** on every span and attribute page (inference, `invoke_agent`, `execute_tool`, `create_agent`, `invoke_workflow` added in v1.41). No public timeline for Stable. Verified https://github.com/open-telemetry/semantic-conventions-genai/blob/main/docs/gen-ai/gen-ai-agent-spans.md ; Verified (May 2026 status) https://greptime.com/blogs/2026-05-09-opentelemetry-genai-semantic-conventions
- Content attributes `gen_ai.input.messages`, `gen_ai.output.messages`, `gen_ai.system_instructions`, `gen_ai.tool.definitions`, `gen_ai.tool.call.arguments/result` are **Opt-In**, flagged "likely to contain sensitive information". Instrumentation-level opt-in is `OTEL_INSTRUMENTATION_GENAI_CAPTURE_MESSAGE_CONTENT=true`; version selection via `OTEL_SEMCONV_STABILITY_OPT_IN=gen_ai_latest_experimental`. The spec recommends external storage with span references for large content. Verified (same URLs).
- Who actually emits content-bearing gen_ai spans/events today:
  - Gemini CLI: native, `gen_ai.client.inference.operation.details` event and `gen_ai.*` span attrs. Verified.
  - hermes-otel plugin: `gen_ai.input.messages`/`output.messages`. Verified (third-party).
  - OpenClaw diagnostics-otel: `gen_ai.tool.call.arguments/result` only when `captureContent`, bounded. Verified.
  - o11y-dev/opentelemetry-hooks (hook adapter, 8 agents): `gen_ai.operation.name` chat/execute_tool/invoke_agent, content only with `IDE_OTEL_CAPTURE_CONVERSATION_CONTENT=true`. Verified https://github.com/o11y-dev/opentelemetry-hooks
  - Claude Code: five gen_ai attributes, content in proprietary attrs. Codex: none. OpenCode: Vercel `ai.*`. Cursor: none.

### 1.3 How close is "one OTLP receiver" to true?

Counting harnesses that can push **full content** (prompt + assistant text + tool I/O) to `localhost:4318` with only a config change:

| Tier | Harnesses | Notes |
|---|---|---|
| Built-in, near-full content | Claude Code (+ Claude Desktop's embedded Claude Code), Gemini CLI | Claude Code's untruncated raw bodies go to **local files**, not OTLP; inline OTLP is 60 KB-truncated per attribute. Tool bodies need the tracing beta. |
| Built-in but experimental / partial | OpenCode (`experimental.openTelemetry`, AI SDK spans with prompts); Codex (prompts only, no assistant text, no tool args) | OpenCode native PR #5245 still open in Sept 2026; feature exists via a different path and is documented by Langfuse. |
| Third-party plugin required | Hermes (hermes-otel), OpenCode (plugins) | Plugin is a user-config line, but the code is not the harness vendor's. |
| Official plugin, content bounded/redacted | OpenClaw | System prompt and thinking never exported. |
| Not available | Cursor CLI (Enterprise-only, no content) | Hooks are the only local path. |

Verdict (Inferred): OTLP-as-one-leg reaches **2 harnesses fully, 3-4 partially, 1 not at all**. It cannot replace the on-disk transcript as the content source for Codex, Cursor, OpenClaw; it can serve as a *second, timestamped, streamed* leg for Claude Code, Gemini, OpenCode, Hermes. Operational caveats for a 168 h unattended run: exporters are push-only with no local spool (Codex "batch asynchronously and flush on shutdown"; hermes-otel flushes at session end); if the local receiver is down the data is gone, except Claude Code `file:` mode. All OTel config is participant-editable, so it is a self-report, not a witness.

### 2.2 Is there a shared spec?

- **No formal cross-vendor hook spec exists.** AAIF (Linux Foundation, Dec 2025) hosts MCP, goose and AGENTS.md; its 2026 program is events and MCP; nothing on hooks. Verified https://www.linuxfoundation.org/press/linux-foundation-announces-the-formation-of-the-agentic-ai-foundation ; https://aaif.io/press/agentic-ai-foundation-announces-global-2026-events-program-anchored-by-agntcon-mcpcon-north-america-and-europe/
- **ACP (Agent Client Protocol)** is editor<->agent JSON-RPC (Zed 1.0 Apr 2026, JetBrains, registry with Claude Code/Codex/Gemini/OpenCode adapters). It streams session updates to an editor, which is a possible *observer* channel, but Claude Code only speaks it through Zed's bridge, and it needs the harness to be launched as an ACP server. Verified https://www.morphllm.com/agent-client-protocol ; https://zed.dev/blog/claude-code-via-acp (Inferred for fit as a recorder)
- **AG-UI** is agent<->frontend event stream (CopilotKit; adopted by LangGraph/Mastra/etc.), not by CLI coding harnesses. Verified https://docs.copilotkit.ai/agentic-protocols/ag-ui
- **IETF draft-sharif-agent-audit-trail-00** (JSON audit records, SHA-256 chain per RFC 8785, optional ECDSA) is an individual Internet-Draft with "no formal standing", expires Sept 29 2026. Verified https://datatracker.ietf.org/doc/draft-sharif-agent-audit-trail/
- **ATIF (Agent Trajectory Interchange Format)**, Harbor v1.8 / NeMo Relay / HF datasets, is a *post-hoc normalization target* for trajectories, not a capture mechanism. Verified https://www.harborframework.com/docs/agents/trajectory-format
- **De facto convergence: the Claude Code dialect.** JSON on stdin, `hook_event_name` + `session_id` + `cwd` (+ `transcript_path`), `tool_name`/`tool_input`/`tool_response`, `prompt`, exit 2 = block, JSON `decision` on stdout. Codex copied it nearly verbatim (including `transcript_path`, `permission_mode`); Copilot and Cursor accept it as an import format; Gemini shares the envelope with different event names; Hermes accepts its output shape; OpenCode has a community shim. Answer (Inferred): yes for six harnesses, the per-harness manifest is a config snippet of ~5-15 lines pointing every event at one command or (Claude Code only) one `http` URL: Claude Code, Codex, Cursor, Gemini, Copilot, Hermes. **Two harnesses need a small code plugin, not a manifest**: OpenCode (JS plugin, or the community `opencode-claude-hooks` shim which is itself a plugin) and OpenClaw (TypeScript plugin registering `api.on`). Claude Desktop and the Codex app inherit the user-level hook files.

What hooks alone do **not** give you, so the transcript reader survives:
- Intermediate assistant text and thinking: only via `transcript_path` (Claude, Codex, Gemini, Copilot; Cursor if transcripts enabled) or OTel.
- Codex assistant text: not in hooks (use `notify` `last-assistant-message` or the rollout JSONL).
- Tokens/model per request: not in hook payloads (Codex/Cursor expose `model`; none expose usage).
- Raw request bodies: nowhere in hooks.
The realistic design is: hooks as the *heartbeat and hash-anchor* (hash `transcript_path` at every event, sign, timestamp), transcripts as the *content*, OTel as an optional third stream where available.

### 3(d) Server request IDs as later-verifiable anchors

- Anthropic: every response carries `request-id: req_...`; SDKs expose `_request_id`; "include this ID when contacting support". Claude Code OTel events include `request_id` **and** `client_request_id` (UUID sent as `x-client-request-id`, v2.1.214+); the raw response body `id` (`msg_...`) is also in `OTEL_LOG_RAW_API_BODIES`. There is **no public endpoint** for it, retention on consumer accounts with training off is 30 days, and it would be a bespoke support/partnership request.

Anthropic's "Built with Opus 4.6" hackathon (Feb 2026) distributed API credits (org-visible), not Max subscriptions. Kaggle rules pages surfaced nothing on vendor-side log verification. **Did anyone converge on one mechanism?** No. Three camps, each still carrying per-harness adapters:
1. Proxies for raw bodies (claude-tap): the only route to *full* request/response bodies for every harness, but needs a base-URL override or a CA-trusting forward proxy, and both are per-harness env/config and are themselves participant-controlled.
2. Hooks to one receiver (o11y-dev, sondera, Braintrust, Langfuse, DEPOSE-active): thinnest adapters, best liveness signal, no raw bodies, no intermediate assistant text without reading `transcript_path`.
3. Transcript-file watchers (agentwatch, DEPOSE-reconstruction, claude-tap-for-Cursor): full content, zero harness config, but nine drifting formats, and this is exactly the status quo.

Why they picked what they picked (Inferred from their docs): observability vendors chose hooks because hooks are the only mechanism present in all six mainstream CLIs with a near-identical JSON shape, and because they fire at turn boundaries (billing and per-developer attribution). Proxy tools chose proxies because they wanted system prompts and thinking blocks, which hooks and OTel do not carry. Nobody chose OTel as the universal leg because only Claude Code, Gemini and (experimentally) OpenCode emit content over it.

## Bottom line for the /goal Cup tracker

1. **OTel is not the one leg.** It is a good second stream for Claude Code (+Desktop), Gemini, OpenCode and, with a third-party plugin, Hermes. Codex sends prompts only, OpenClaw sends bounded content, Cursor sends nothing locally.
2. **Hooks are the closest thing to a standard.** Claude Code's JSON-on-stdin dialect is copied by Codex, imported by Cursor and Copilot, envelope-shared by Gemini, output-compatible with Hermes. One receiver plus ~10-line manifests covers six harnesses; OpenCode and OpenClaw need a ~50-line plugin each. Hooks hand you `transcript_path`, so the tracker can hash the transcript at each event, which is the cheapest tamper-evidence primitive available without a proxy.
3. **No provider-side witness is obtainable by a consumer subscription today.** Exports omit CLI sessions, no usage API is reachable, local sessions are not synced. The only latent witness is the server `request-id` / `x-request-id` pair (plus Claude Code's `client_request_id`), which both vendors already use for support lookups; confirming them would be a bespoke, consented request with a 30-day retention clock and no precedent found.
