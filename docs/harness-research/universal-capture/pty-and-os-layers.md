# Universal (below-the-harness) witness layers for the /goal Cup tracker

Research notes, 2026-09-10. Labels: **Verified** = read in a primary or near-primary source (URL given); **Inferred** = follows from verified facts or from how the mechanism works, not directly documented; **Unknown** = could not establish.

Local inspection (read-only, this Mac): macOS 26.5.2 arm64, SIP enabled. Present: `/usr/bin/script`, `/usr/bin/expect`, `/usr/bin/screen`, `/opt/homebrew/bin/tmux`, `/usr/bin/sandbox-exec` (man page says DEPRECATED but binary and `sandbox(7)` still ship), `/usr/bin/fs_usage` (man: "requires root privileges"), `/usr/bin/opensnoop` (man: DTrace, root), `/usr/bin/tmutil`, `/sbin/pfctl`. Not installed: asciinema, `container`, limactl, docker, orb.

## A. PTY ownership as the human-input chokepoint

### A1. Do the TUI harnesses run correctly inside a wrapping pty?

Baseline fact: every one of these harnesses is already used daily under a nested pty owned by something other than the terminal emulator (tmux, screen, VS Code/Cursor integrated terminal via node-pty, ssh, asciinema). A tracker that opens a pty pair, puts its own stdin in raw mode, forwards bytes verbatim in both directions, and forwards SIGWINCH as `TIOCSWINSZ` on the master is functionally what tmux-without-a-screen-model or asciinema does. The failure modes reported in the wild come from wrappers that *interpret* the stream (tmux, zellij, psmux), not from transparent byte proxies.

| Harness | TUI stack | Terminal features it uses | Known nested-pty issues |
|---|---|---|---|
| Claude Code | Node + Ink/React | raw mode; bracketed paste (`\x1b[?2004h`); Kitty keyboard protocol since 2.1.0 for Shift+Enter (CSI u); mouse tracking in some builds; no alt-screen by default | tmux mouse capture breaks scrollback (**Verified** https://github.com/anthropics/claude-code/issues/38810); bracketed-paste mishandling in VS Code terminal / accessibility tools (**Verified** https://github.com/anthropics/claude-code/issues/13183, /3134); Ctrl-G external editor leaves bracketed paste on (**Verified** /24418); large paste freezes Cursor's node-pty by backpressure (**Verified** /34529); Kitty protocol detection reads env vars like `TERM_PROGRAM`/`KITTY_WINDOW_ID` (**Verified** /27868), which a wrapper inherits unchanged; "Raw mode is not supported" only when stdin is not a tty (**Verified** /5925, /1072) — a pty slave *is* a tty, so this does not apply. |
| Codex CLI | Rust + ratatui/crossterm | alternate screen, mouse capture, manual scrollback | alt-screen/scrollback problems in zellij (**Verified** https://github.com/openai/codex/issues/2836, /24552); psmux forwarded mouse reports and Codex lost its transcript (**Verified** https://github.com/psmux/psmux/blob/master/docs/faq.md); resize events can get stuck behind "tmux, screen, zellij, SSH, or WSL" pty layers, Ctrl-L redraw workaround (**Verified** https://aident.ai/blog/fix-codex-terminal-stuck-after-resize). |
| OpenCode | TUI client + local HTTP server (Bun) | full-screen TUI | none specific found (**Unknown**). |

**Inferred:** a transparent proxy (portable-pty/`openpty` + raw-mode stdin + SIGWINCH forwarding) will not trigger the tmux/zellij class of bugs because it does not consume mouse or alt-screen sequences. The Kitty keyboard negotiation (`\x1b[?u` query / response) and terminal-identity queries pass through untouched, so Shift+Enter keeps working exactly as it does in the participant's real terminal. The one thing that changes is `$TERM_PROGRAM`-style env detection only if the tracker scrubs env; it should not.

**Verified caveat for macOS `script -k`:** the man page says echo-cancellation in `-k` mode "does not work when the terminal is in a raw mode where the program being run is doing manual echo" — irrelevant if the tracker records the raw input stream separately from output rather than relying on `script`'s merged typescript.

### A2. Can the input side distinguish a submitted message from chords/paste/navigation?

Short answer: do not try to parse TUI semantics in the tracker. Record raw input bytes with timestamps (asciicast v3 `"i"` events are exactly this: "raw data sent from a terminal emulator to stdin of the recorded program", **Verified** https://docs.asciinema.org/manual/asciicast/v3/) and reconstruct offline against the harness's own transcript.

Reconstruction model (**Inferred**, straightforward):

- The harness transcript is the ground truth for *what* the model received as a user turn (Claude Code JSONL `~/.claude/projects/<proj>/<session>.jsonl`, **Verified** https://code.claude.com/docs/en/sessions; Codex `~/.codex/sessions/YYYY/MM/DD/rollout-*.jsonl`, third-party **Verified** https://jazzyalex.github.io/agent-sessions/guides/codex-local-history.html; OpenCode `~/.local/share/opencode/storage/{session,message,part}/`; Hermes `~/.hermes/state.db` SQLite with a `source` platform column, **Verified** https://hermes-agent.nousresearch.com/docs/user-guide/sessions; Cursor `~/.cursor/chats/<md5>/<id>/store.db` + `~/.cursor/projects/<p>/agent-transcripts/<id>/<id>.jsonl`, third-party **Verified** https://github.com/Callum-Ward/cursaves/blob/main/docs/how-cursor-stores-chats.md; OpenClaw `~/.openclaw/agents/<id>/agent/openclaw-agent.sqlite`, **Verified** https://docs.openclaw.ai/concepts/session).
- For each user turn with timestamp T, the pty input log must contain, in a window before T, printable bytes whose text matches the turn (after stripping editing keys), followed by a submit key: CR `0x0d`, or CSI-u Enter `\x1b[13u` / `\x1b[13;1u` when Kitty protocol is active; Shift+Enter is `\x1b[13;2u` (newline, not submit). Paste arrives as `\x1b[200~ ... \x1b[201~` and is trivially identified.
- The Cup rule makes this far easier than general reconstruction: every user turn other than the initial prompt must equal "keep going". So the classifier is: (a) any transcript user turn that is not the seed prompt or "keep going" = violation regardless of the pty; (b) any "keep going" turn with no matching typed bytes in the pty log = injected from elsewhere (flag); (c) any substantial typed input in the pty log with no corresponding transcript turn = the human typed into something else inside the pty (nested shell via Claude Code `!` bash mode, Ctrl-G `$EDITOR`, permission-prompt answers, slash commands) — most are benign but Ctrl-G editor and `!` are real holes (text reaches the model via a temp file / shell output) and should be policy-banned or flagged.
- Timing is a second signal: human typing has inter-key gaps; harness-generated user slots (`/loop`, scheduled tasks, summaries, hook stdout) have no pty bytes at all, which is exactly the "harness writes its own text into the user slot" case the current hook approach could not separate.

Things that are genuinely hard (**Inferred**): non-Latin IMEs deliver composed text at once (looks like paste); voice-to-text tools inject via paste; readline-style editing (Ctrl-W, arrows) means byte-for-byte matching needs a small line-editor emulation or fuzzy match. Acceptable for a "keep going"-only regime.

Rule of thumb that holds for every harness examined: **every bypass still lands in the harness's own persistent session store as a user-side turn** (that store is what the model is replayed from), so "transcript turn present + no matching pty bytes" is a valid flag. The exceptions are where the harness itself is not the process in the pty (OpenClaw; Claude Code background sessions; Codex `--remote`).

**tmux/screen started inside the pty (question asked explicitly):** confirmed by construction — tmux's client process reads its keyboard from the pty slave the tracker owns, so every byte still traverses the tracker's master; and asciinema's own docs describe recording a tmux session by wrapping the `tmux attach` client (**Verified** https://github.com/asciinema/asciinema/wiki/Recording-tmux-session). The hole is *detach*: the tmux server (and the harness inside it) survives after the client exits, and a second `tmux attach` from an un-tracked terminal reaches the same harness. Detection: the harness process is now a child of the tmux server (reparented out of the tracker's process group); `tmux` binary in the process tree; the pty session ends while the transcript keeps growing. Policy: forbid multiplexers inside the tracked pty, or make the tracker refuse to start if `tmux`/`screen` appears in the tree.

**SSH into the machine** is the same case as "another terminal": the harness would have to be resumed/attached from that shell; covered by the process/transcript checks above.

### A4. Is the screen-output side useful evidence?

Yes, as a third leg, but not as a primary record.

- What it uniquely captures (**Verified** from the docs cited above): the rendered inbound lines for channels (`← telegram …`), cross-session messages (`› Message from @…`), the `/rc active` footer, "Remote Control not started here" notices, permission prompts and the human's answers, `!` shell mode, Ctrl-G editor sessions, and the harness's own echo of the user's message in the input box. In other words, it shows what the *human saw*, which the JSONL does not.
- Cost/noise: Ink redraws whole regions (blit disabled on some terminals → 100% redraws, **Verified** https://github.com/anthropics/claude-code/issues/27360), and Codex is alt-screen so the output stream is a sequence of frame diffs, not a transcript. Over 168 h this is hundreds of MB to a few GB raw; it compresses very well (zstd) and asciicast v3's `o` events are already the natural container. Making it human-readable requires replaying through a VT parser (asciinema player, or the `vt100`/`alacritty_terminal` crates offline) — feasible, do it at judging time, not at capture time.
- Recommendation (**Inferred**): capture `i`, `o`, `r`, `x` events (asciicast v3 shape) into the hash chain; index the `o` stream only for anomaly triage (grep for the marker strings above), and use the harness transcript + `i` stream as the primary evidence.

### A5. Existing tools

- asciinema 3.x (Rust): `rec -I/--capture-input` (renamed from `--stdin`), asciicast v3 with `o/i/r/m/x` events, macOS/Linux/FreeBSD, **"Windows is currently not supported"** (**Verified** https://github.com/asciinema/asciinema, https://blog.asciinema.org/post/three-point-o/, https://docs.asciinema.org/manual/asciicast/v3/). Input capture is off by default because "it's basically key-logging (scoped to a single shell instance)" — exactly the scope you want.
- macOS `script -r` (record input+output+timing) / `-k` / `-F` flush (**Verified** local man page). util-linux `script --log-in/--log-out/--log-io/--log-timing`, multi-stream timing format since 2.35, with the explicit warning that input logs capture passwords regardless of echo (**Verified** https://man7.org/linux/man-pages/man1/script.1.html).
- tlog (Red Hat session recording): logs "user input, program output, and terminal window size changes" as JSON (**Verified** https://www.mankier.com/8/tlog-rec-session). ttyrec: output-only, legacy.
- Teleport Enhanced Session Recording: eBPF exec/open/connect events correlated to a session by cgroup v2, plus seccomp to drop the `bpf` syscall so the user can't unload the probes (**Verified** https://goteleport.com/blog/enhanced-session-recording/). This is the closest precedent to "tamper-evident session audit", but it is Linux + root.
- iTerm2 automatic session logging (raw or plain text per profile) (**Verified** https://iterm2.com/documentation-preferences-profiles-session.html) — terminal-scoped, depends on the participant's emulator; Warp has no log-to-file (**Verified** https://github.com/warpdotdev/warp/issues/385).
- Agent-specific: coder/agent-tty (record terminal sessions as reviewable evidence, **Verified** https://github.com/coder/agent-tty); cc-prism (renders Claude Code JSONL *into* asciicasts, i.e. the opposite direction, https://github.com/gulp/cc-prism/); WorkOS "audit harness" for Claude Code/Codex/OpenClaw (hook/log based, https://workos.com/blog/audit-trail-for-every-coding-agent); agent-sessions (reads the local stores of Codex/Claude/Cursor, https://jazzyalex.github.io/agent-sessions/). No project found that uses pty recording as an anti-collusion audit for coding agents (**Unknown** = none found).
- Rust building blocks: `portable-pty` (wezterm; Unix openpty + ConPTY), `pty-process`, `nix::pty`, `vt100` for replay, `libproc`/`sysinfo` for process trees, `notify` for FSEvents.

### B2. Process

- `proc_listpids` / `proc_pidinfo` via the `libproc` crate work unprivileged for the caller's own uid (**Verified** https://github.com/andrewdavidmackenzie/libproc-rs). The tracker, as the pty session leader, can walk its descendants (ppid chain) and detect: a second harness binary, `tmux`/`screen`, `hermes gateway`, `openclaw gateway`, `codex app-server`, the Claude Code background supervisor, or a child that reparented to launchd (pid 1) = escaped the process group.
- Process-group kill (`killpg`) covers everything still in the group; anything that `setsid`'d (tmux server, Claude background supervisor) is out of reach and must be detected instead (**Inferred**).
- Privacy tension: enumerating *all* of the user's processes to find a second harness is system-wide observation. Recommend recording only (a) the tracked subtree in full and (b) for other processes, just a boolean "another process with executable ∈ {claude, codex, opencode, hermes, openclaw, agent} and cwd == workspace exists", never names/args of unrelated processes.

### B4. Tracker-built VM/container for CLI harnesses

Options on this Mac: Apple `container` (macOS 26; one lightweight VM per container on Virtualization.framework, vmnet networking, virtiofs mounts; port publishing has had breakage — "accepts connections but doesn't forward" on 26.1 (**Verified** https://github.com/apple/container/issues/919, https://github.com/apple/container/blob/main/docs/technical-overview.md); Unix-socket publishing as alternative; memory freed in the guest is not returned to the host (**Verified** technical overview)); OrbStack (single VM, virtiofs, near-native bind-mount speed, on-demand RAM); Docker Desktop (slower bind mounts, 3-4x on file-heavy work); Lima (plain VM, most controllable, most manual). Comparison sources: https://www.repoflow.io/blog/apple-containers-vs-docker-desktop-vs-orbstack, https://sliplane.io/blog/orbstack-vs-docker.

What the VM buys: the tracker owns the filesystem (bind-mount only the workspace), the pty (container `exec -t`), and egress (Anthropic's reference devcontainer does exactly this with an iptables/ipset allowlist requiring `NET_ADMIN`/`NET_RAW` in the container, **Verified** https://code.claude.com/docs/en/devcontainer). Claude Code's cross-session messaging cannot cross the container boundary (**Verified**). Background sessions and tmux inside the container are still inside the tracked filesystem.

What breaks or needs work:

- **Auth, Claude Code:** browser OAuth needs a localhost callback; the devcontainer doc gives the fallback: "copy the code shown in the browser and paste it at the `Paste code here if prompted` prompt" (**Verified**). `claude setup-token` yields a long-lived OAuth token for Pro/Max (1 year), exported as `CLAUDE_CODE_OAUTH_TOKEN` (**Verified** https://code.claude.com/docs/en/devcontainer, https://codeongrass.com/blog/how-to-run-claude-code-on-a-remote-server/). No keychain on Linux; credentials live in `~/.claude/.credentials.json` in the volume. Remote Control needs feature-flag fetching, which works from a container unless telemetry vars are set (**Verified**).
- **Auth, Codex:** `codex login --device-auth` (device code, 15 min, no network path needed) (**Verified** https://developers.openai.com/codex/auth); but device auth can be disabled by a ChatGPT workspace admin (**Verified** https://github.com/openai/codex/issues/9253); otherwise forward port 1455 (`--publish 1455:1455`, subject to the Apple `container` port bug).
- **GUI harnesses** (Claude Desktop, Codex app): cannot run in a Linux guest; transcript-only witness on the host.
- **Participant tooling:** the agent building a product needs Node/Python/Docker. Docker-in-Docker needs a privileged container, a mounted host Docker socket, or Sysbox (**Verified** https://github.com/nestybox/sysbox/blob/master/docs/user-guide/dind.md). Under OrbStack/Docker Desktop a socket mount works; under Apple `container` there is no nested-Docker story found (**Unknown**). Browsers for the agent (Playwright) are fine in Linux; anything macOS-native (Xcode, simulators) is impossible.
- **168 h on a laptop:** sleep/wake, macOS updates, VM memory growth. Apple `container` at 0.x and the guest-memory-not-relinquished note are red flags for a week-long run; OrbStack is the most battle-tested for long-lived dev containers (**Inferred**).
- **Consumer-subscription legality:** setup-token / device-auth are documented paths for Pro/Max and ChatGPT plans, so nothing here requires API keys (**Verified** above).

Precedent: Anthropic devcontainer (above); Claude Code on the web and Codex cloud (vendor cloud sandboxes, not local); Docker "Sandboxes for Codex CLI" microVMs (https://codex.danielvaughan.com/2026/04/13/docker-sandboxes-codex-cli-microvm-isolation/); OpenHands docker runtime; E2B (Firecracker) and Daytona (Docker; source closed June 2026) as hosted sandboxes (https://northflank.com/blog/daytona-vs-e2b-ai-code-execution-sandboxes). OpenAI's Agents SDK v2 ships seven sandbox providers natively (same source). All of these are "agent in a box" for safety; none is built as a *witness* — the tracker would be the first to use the box as an evidence boundary.

## C. Windows / Linux parity

### Linux (second priority)

- pty: `openpty` + raw stdin, identical to macOS. util-linux `script --log-in/--log-out/--log-io/--log-timing` is a ready-made three-stream recorder (**Verified** above); asciinema 3 supported; tlog available on RHEL-family.
- Sandbox without root: bubblewrap + seccomp (Claude Code sandbox-runtime, needs unprivileged user namespaces, which some distros restrict) and Landlock + seccomp (Codex `codex-linux-sandbox` helper) (**Verified** above). Landlock is the cleanest folder-scoped write fence available to an unprivileged tracker on kernels ≥5.13 (**Inferred**).
- Filesystem: inotify (unprivileged, per-directory watch limits); fanotify needs `CAP_SYS_ADMIN`.
- Process: `/proc` gives full trees unprivileged; cgroup v2 can group the pty session if the user has a delegated cgroup (systemd user slices do this by default) — the Teleport approach correlates eBPF events by cgroup (**Verified**), but loading eBPF needs `CAP_BPF`/root, so treat eBPF as an optional hardening tier, not a baseline. ptrace works unprivileged on own children but is intrusive and slow; not recommended.
- Cross-session messaging socket lives in `/tmp/cc-socks-<uid>` on Linux too (**Verified**); same `refuse` mitigation.

### Windows (third priority)

- ConPTY: the tracker calls `CreatePseudoConsole` and owns both pipes; the host writes VT input to the input pipe and ConPTY converts it to `INPUT_RECORD`s, so every keystroke is visible to the host by construction (**Verified** https://learn.microsoft.com/en-us/windows/console/creating-a-pseudoconsole-session, https://devblogs.microsoft.com/commandline/windows-command-line-introducing-the-windows-pseudo-console-conpty/). Nesting a ConPTY inside Windows Terminal is the everyday case (VS Code integrated terminal does it), so it works, but ConPTY re-renders output and has documented alternate-buffer/resize quirks (**Verified** https://github.com/microsoft/terminal/issues/4389, /235).
- Claude Code on native Windows has a stack of ConPTY-specific rendering/perf bugs (white input bar, frozen input in 2.1.30, keystroke lag, non-functional blitting) (**Verified** https://github.com/anthropics/claude-code/issues/14599, /23211, /41501, /27360). Participants will blame the tracker for these; document that they reproduce without it.
- Recorders: asciinema does not run on Windows; PowerSession is the ConPTY-based alternative (**Verified** asciinema README); `portable-pty` covers ConPTY for a Rust tracker.
- Sandbox: Codex has a Windows sandbox implementation (restricted-token based per the platform write-up, **Inferred**); Claude Code's sandbox is macOS/Linux only (**Unknown** on native Windows; WSL2 works as Linux). Job Objects with kill-on-close are the equivalent of process-group containment (**Inferred**).
- Claude Code cross-session messaging on Windows uses a named pipe and requires the auth token line (**Verified**), same `refuse` mitigation.

## Bottom line

1. A transparent tracker-owned pty is a sound *universal* human-input witness for the CLI harnesses that actually run in the pty (Claude Code, Codex CLI, OpenCode TUI, Hermes TUI, Cursor `agent`). It sees every byte the human types and never injects anything. Record raw input bytes and reconcile offline against the harness's own session store; do not parse TUI semantics live.
2. It is *not* sufficient alone. The bypasses that matter are the ones where the process in the pty is not the only writer to the session: Claude Code Remote Control / Channels / cross-session socket / background supervisor / `--resume --force`; Codex desktop app or a second `codex resume` between turns; OpenCode's always-on HTTP server; Hermes gateway re-binding; OpenClaw where the Gateway, not the TUI, is the agent. Every one of these still lands in the local session store, so the tracker's second leg (hash-chained session-store capture) turns "turn present, no pty bytes" into a mechanical flag. Add folder-scoped hardening where it exists (`crossSessionInbound: refuse`, env vars that disable RC, argv inspection for `--channels`/`--remote`/`--bg`, process-tree checks for tmux/gateways/supervisors).
3. Seatbelt (`sandbox-exec`) is the one process-scoped, root-free, SIP-compatible enforcement layer on macOS and both Anthropic and OpenAI ship on it; use it for egress logging/denial rather than pf or Network Extensions.
4. A tracker-built Linux container (OrbStack or Lima, with the Anthropic devcontainer firewall pattern) is realistic for Claude Code and Codex on consumer subscriptions thanks to `claude setup-token` / paste-code login and `codex login --device-auth`, and it closes the messaging and tmux holes by construction. It costs GUI harnesses, macOS-native tooling, Docker-in-Docker friction, and a week of VM uptime risk; offer it as the "strict tier", not the only tier.
