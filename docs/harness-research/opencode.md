## 1. On-disk session storage

**Location and engine (High).** SQLite at `~/.local/share/opencode/opencode.db` (`Global.Path.data` = `xdgData/opencode`; `Database.path()` = `join(Global.Path.data, "opencode.db")`; pragmas `journal_mode=WAL`, `synchronous=NORMAL`, `busy_timeout=5000`, `foreign_keys=ON`). SRC: `packages/core/src/global.ts` L10-11, `packages/core/src/database/database.ts` L27-31, L53. Drizzle ORM over SQLite (`packages/core/src/session/sql.ts` L1). The official troubleshooting doc still describes the old JSON layout (`~/.local/share/opencode/project/<slug>/storage/`) and never mentions SQLite ([docs/troubleshooting](https://opencode.ai/docs/troubleshooting/)) — it is stale. Migration to SQLite shipped in v1.2.0 (Feb 2026): [dax's post](https://x.com/thdxr/status/2022562561732812841), [issue #13636](https://github.com/anomalyco/opencode/issues/13636), [issue #13654](https://github.com/anomalyco/opencode/issues/13654) (incremental upgrades silently skipped the import). `opencode db [query] --format json|tsv` opens the DB or runs SQL directly (SRC: `packages/opencode/src/cli/cmd/db.ts`). The legacy JSON `Storage` module still exists and is still written for `session_diff` (SRC: `packages/opencode/src/session/revert.ts` L77) but messages/parts are read from SQLite.

**Schema (High).** SRC: `packages/core/src/session/sql.ts`.
- `session`: `id, project_id, workspace_id, parent_id, slug, directory, path, title, version, share_url, summary_*, metadata(json), cost, tokens_*, revert(json), permission(json), agent, model(json {id, providerID, variant}), time_created, time_updated, time_compacting, time_archived`; index `session_parent_idx` on `parent_id`.
- `message`: `id, session_id, time_created, time_updated, data(json)` where `data` = the v1 message `Info` minus id/sessionID.
- `part`: `id, message_id, session_id, time_*, data(json)` = v1 `Part` minus ids.
- `event` / `event_sequence`: append-only durable event log (`id, aggregate_id, seq, type, data(json)`; unique `(aggregate_id, seq)`), aggregate = sessionID. SRC: `packages/core/src/event/sql.ts`.
- Newer v2 tables also present: `session_message` (`type, seq, data`), `session_input` (`prompt, delivery ∈ {steer, queue}, admitted_seq, promoted_seq`), `session_context_epoch` (`baseline, snapshot, baseline_seq`), `todo`. SRC: `sql.ts`; `packages/schema/src/session-delivery.ts` L5.

**Message/part content (High).** SRC: `packages/schema/src/v1/session.ts`.
- `UserMessage` (L332-355): `id, sessionID, role:"user", time.created, format?, summary?, agent, model{providerID, modelID, variant?}, system?, tools?`. **No `source`/`origin` field.**
- `AssistantMessage` (L453-488): `parentID (user msg id), modelID, providerID, mode, agent, path{cwd, root}, summary?, cost, tokens{input, output, reasoning, cache{read, write}}, structured?, variant?, finish?, error?, time{created, completed?}`.
- Parts: `text{text, synthetic?, ignored?, metadata?}`, `reasoning`, `file`, `agent`, `subtask{prompt, description, agent, model?, command?}`, `retry`, `compaction{auto, overflow?, tail_start_id?}`, `snapshot`, `patch`, `step-start{snapshot?}`, `step-finish{reason, cost, tokens}`, `tool{callID, tool, state, metadata?}` with `state.status ∈ pending|running|completed|error`, `state.input`, `state.output` (string), `state.error`, `attachments?` (L102-331).

**Completeness gaps (High).**
- **System prompt is not persisted** in message rows. It is assembled per request in memory; only an optional caller-supplied `user.system` string is stored on the user message. SRC: `packages/opencode/src/session/prompt.ts` (assistant Info has no `system`), `packages/opencode/src/session/llm/request.ts` L61-62. `session_context_epoch.snapshot` stores a `SystemContext.Snapshot` (record of source key → `{value: Json, removed?}`), with builtin keys `core/environment`, `core/date`, `core/builtins` (SRC: `packages/core/src/system-context/builtins.ts` L26-42, `index.ts` L49-57) — a structured baseline, not the rendered prompt text.
- **AGENTS.md/instructions text** is not stored per message (loaded at request time).
- **Provider request/response payloads** are not persisted anywhere (only via OTEL, §3).
- **Tool outputs are truncated in the part**: default `MAX_LINES=2000`, `MAX_BYTES=50KB`; the full text is written to `~/.local/share/opencode/tool-output/` with 7-day retention, and the part's `output` gets a preview plus "Full output saved to: <file>". SRC: `packages/opencode/src/tool/truncate.ts` L14-15, L36-37, L130; `truncation-dir.ts` L4; `packages/core/src/tool-output-store.ts` L13-15. Configurable via `tool_output.max_lines/max_bytes`.
- Reasoning parts are stored when the provider returns them (`ReasoningPart`, L118).

**Write semantics (High).** `message`/`part` rows are **upserts** (`insert … onConflictDoUpdate({set:{data}})`) driven by `message.updated`/`message.part.updated` events (SRC: `packages/core/src/session/projector.ts` L267-270, L318-321). `message.removed` deletes rows (L274+). `/undo` (revert) deletes messages/parts after the boundary (SRC: `packages/opencode/src/session/revert.ts` L108-119). **However**, `session.created/updated/deleted`, `message.updated`, `message.removed`, `message.part.updated`, `message.part.removed` are all declared `durable` (aggregate `sessionID`) and every publish appends a row to `event` with a monotonic `seq` (SRC: `packages/schema/src/v1/session.ts` events block spreads `...options` with `durable:{aggregate:"sessionID", version:1}`; `packages/core/src/event.ts` L336-348). So the `event` table is an append-only log of every message/part snapshot including tool outputs. It is only deleted via `remove(aggregateID)` (L513-519) — I did not trace what calls it; assume session deletion. `message.part.delta`, `session.diff`, `session.error` are not durable (v1/session.ts L633-652).

**Subagents (High).** Task tool creates a child via `sessions.create({parentID: ctx.sessionID, title: "<desc> (@<agent> subagent)", agent, permission})`; the parent tool part's `metadata` = `{parentSessionId, sessionId, model, background?}`. SRC: `packages/opencode/src/tool/task.ts` L157-190. Child sessions have `session.parent_id`; `GET /session/:id/children` lists them ([docs/server](https://opencode.ai/docs/server/)). Subagent model defaults to the invoking assistant's `providerID/modelID` (task.ts L181-184; [docs/agents](https://opencode.ai/docs/agents/)).

## 2. Plugin / hooks API

**Hooks (High).** SRC: `packages/plugin/src/index.ts` L223-334. `event({event})`, `config`, `tool`, `auth`, `provider`, `chat.message(input{sessionID, agent?, model?, messageID?, variant?}, output{message: UserMessage, parts: Part[]})`, `chat.params(input{sessionID, agent, model, provider, message}, output{temperature, topP, topK, maxOutputTokens, options})`, `chat.headers(same input, output{headers})`, `permission.ask(Permission, {status})`, `command.execute.before`, `tool.execute.before(input{tool, sessionID, callID}, output{args})`, `tool.execute.after(input{tool, sessionID, callID, args}, output{title, output, metadata})`, `shell.env`, `tool.definition`, `experimental.chat.messages.transform({}, {messages:[{info, parts}]})`, `experimental.chat.system.transform({sessionID?, model}, {system: string[]})`, `experimental.session.compacting`, `experimental.compaction.autocontinue`, `experimental.provider.small_model`, `experimental.text.complete`, `dispose`. Plugin input: `{client, project, directory, worktree, serverUrl, $, experimental_workspace}`.

**What is exposed (High).** `experimental.chat.system.transform` receives the **full system prompt array** for every request (called in `packages/opencode/src/session/llm/request.ts` L69-73) and `experimental.chat.messages.transform` the **full message history sent to the model** — together these are the only place the exact model input is observable without a proxy. `chat.params`/`chat.headers` get `model` (full Model object) and the user message. `tool.execute.after` gets the **untruncated** tool output? — not verified; the hook receives `output` before/after truncation is unknown (Low). `event` receives every EventV2 event for the instance directory (`packages/opencode/src/plugin/index.ts` L255-261).

**Loading (High).** Sources: `plugin` array in `opencode.json` (npm spec or `[spec, options]`), `.opencode/plugin(s)/*.{ts,js}` under the project and global config dirs (`Glob.scan("{plugin,plugins}/*.{ts,js}")`; SRC: `packages/opencode/src/config/plugin.ts` L21-27, `config.ts` L476-478; [docs/plugins](https://opencode.ai/docs/plugins/) lists `~/.config/opencode/plugins/` and `.opencode/plugins/`, order: global config, project config, global dir, project dir). Also `OPENCODE_CONFIG`, `OPENCODE_CONFIG_CONTENT` env ([docs/config](https://opencode.ai/docs/config/)). Plugins load **once per Instance** inside `InstanceState.make` (SRC: `plugin/index.ts` L134, L181-187) and hooks run in the server process. `flags.pure` disables external plugins (L181) — a participant with `OPENCODE_PURE`-style flag could drop them; verify the env name (Low).

**Mid-run edits / hot reload (Medium).** No config file watcher; hot-reload issue closed as not planned ([#22213](https://github.com/anomalyco/opencode/issues/22213); also [#10899](https://github.com/anomalyco/opencode/issues/10899)). But the config **can** be reloaded without restart: the TUI worker exposes `reload()` → `cfg.invalidate()` + dispose all instances (SRC: `packages/opencode/src/cli/tui/worker.ts` L62-70), and HTTP `POST /instance/dispose`, `POST /global/dispose` exist (SRC: `groups/instance.ts` L44, `groups/global.ts` L72). Disposing and re-loading an instance re-runs plugin loading with the edited config. So plugin removal mid-run is feasible for a participant without killing the process.

**Bus event types (High).** SRC: grep of `packages/schema/src/*.ts`: `server.connected, server.heartbeat, server.instance.disposed, session.created/updated/deleted/diff/error/idle/status/compacted, message.updated, message.removed, message.part.updated, message.part.delta, message.part.removed, permission.asked/replied, permission.v2.asked/replied, question.*, todo.updated, file.edited, file.watcher.updated, command.executed, lsp.updated, mcp.tools.changed, installation.*, plugin.added, project.updated, pty.*, vcs.branch.updated, workspace.*, worktree.*, tui.command.execute, tui.prompt.append, tui.session.select, tui.toast.show`, plus the v2 family `session.next.{prompted, prompt.admitted, synthetic, context.updated, model.switched, agent.switched, moved, shell.started/ended, step.started/ended/failed, text.started/delta/ended, reasoning.*, tool.input.*, tool.called/progress/success/failed, retried, compaction.*, revert.*}`.

## 3. Telemetry / OpenTelemetry

**Native (High).** `experimental.openTelemetry: true` in config enables Vercel AI SDK `experimental_telemetry` on `streamText` with `functionId: "session.llm"`, metadata `{userId, sessionId}` (SRC: `packages/opencode/src/session/llm.ts` L208-209, L344-351; config schema description at `packages/core/src/v1/config/config.ts` L173-174; [opencode.ai/config.json](https://opencode.ai/config.json)). Export is only wired when `OTEL_EXPORTER_OTLP_ENDPOINT` is set: traces to `${endpoint}/v1/traces` via `@opentelemetry/exporter-trace-otlp-http`, logs to `/v1/logs`; resource attrs include `opencode.client`, `opencode.run`; `OTEL_EXPORTER_OTLP_HEADERS`, `OTEL_RESOURCE_ATTRIBUTES` honored (SRC: `packages/core/src/observability/otlp.ts`). Maintainer confirmation of this two-part setup: [PR #5245 comments](https://github.com/anomalyco/opencode/pull/5245) (PR itself still open, not merged); native OTEL issue [#12142](https://github.com/anomalyco/opencode/issues/12142) closed as not planned. The AI SDK spans (`ai.streamText`, `ai.toolCall`, `ai.streamText.doStream`) carry prompt text per the PR discussion — I did not verify `recordInputs/recordOutputs` defaults in the vendored SDK (Medium). Langfuse's integration relies on this: ["OpenCode has experimental OpenTelemetry support"](https://langfuse.com/integrations/developer-tools/opencode).

**No default phone-home** telemetry found; enterprise doc says processing is local/direct-to-provider ([docs/enterprise](https://opencode.ai/docs/enterprise/)). `share: "auto"` would upload the whole session to `https://opncd.ai` (SRC: `packages/opencode/src/share/share-next.ts` L210, L293-299; [docs/share](https://opencode.ai/docs/share/)).

## 4. Headless / server modes

**`opencode run` (High).** Flags: `--format default|json`, `--continue/-c`, `--session/-s`, `--fork`, `--share`, `--model/-m`, `--agent`, `--file/-f`, `--title`, `--command`, `--attach <url>`, `--username/--password`, `--dir`, `--port`, `--variant`, `--thinking`, `--auto`, `--yolo`, `--dangerously-skip-permissions`, `--mini`, `--replay`, `--replay-limit`, `--demo` ([docs/cli](https://opencode.ai/docs/cli/); SRC: `packages/opencode/src/cli/cmd/run.ts`). Global: `--print-logs`, `--log-level`. Non-interactive mode sends **one** prompt via `client.session.prompt({sessionID, agent, model, variant, parts:[...files, {type:"text", text}]})` and exits on `session.status` idle (run.ts L864-870, L794). `--format json` emits **only** `tool_use`, `step_start`, `step_finish`, `text`, `reasoning`, `error` lines `{type, timestamp, sessionID, ...}` (L678-688) — not the raw SSE stream, and the harness's own prompt is not echoed. Stdin is read when piped.

**`opencode serve` (High).** `--port` (default 4096), `--hostname` (127.0.0.1), `--cors`, `--mdns`; basic auth via `OPENCODE_SERVER_PASSWORD`/`OPENCODE_SERVER_USERNAME` (SRC: `packages/opencode/src/server/auth.ts` L18-19). Endpoints: `GET /event` (SSE; first event `server.connected`, then bus events filtered to the instance directory, heartbeat every 10s; SRC: `handlers/event.ts`), `GET /global/event` (all GlobalBus events; `handlers/global.ts`), `GET/POST /session`, `GET /session/:id`, `GET /session/:id/children`, `GET /session/:id/message?limit`, `POST /session/:id/message` (body `{messageID?, model?, agent?, noReply?, tools?, format?, system?, variant?, parts}` — SRC: `packages/sdk/js/src/v2/gen/types.gen.ts` L9796-9809; `prompt.ts` L1501-1512), `POST /session/:id/prompt_async`, `POST /session/:id/command`, `POST /session/:id/abort`, `GET /doc` OpenAPI ([docs/server](https://opencode.ai/docs/server/)). `POST /sync/history` returns rows from the durable `event` table ordered by `seq` (SRC: `handlers/sync.ts` L74-90) — a replayable export of the full session log.

**Does `/event` carry full text? (High)** Yes for `message.part.updated`: the payload is the whole part (`{sessionID, part: structuredClone(part), time}`, SRC: `packages/opencode/src/session/session.ts` publish sites) so completed text/tool parts arrive in full; `message.part.delta` carries streaming deltas. The SSE handler forwards every EventV2 event without type filtering (`handlers/event.ts` L34-38).

**`opencode export [sessionID] [--sanitize]`** writes `{info, messages:[{info, parts}]}` to stdout for **one** session, no children (SRC: `cli/cmd/export.ts` L224-290). `opencode import <file|shareURL>` writes sessions/messages into the DB (`cli/cmd/import.ts` L96-185). SDK: `createOpencodeClient({baseUrl})`, `event.subscribe()`, `session.messages/children/prompt` ([docs/sdk](https://opencode.ai/docs/sdk/)).

## 5. Model identity (High)

Every assistant message stores `providerID` + `modelID` (+ `variant`, `agent`, `mode`) (`v1/session.ts` L461-465; set in `prompt.ts` from the resolved model). Every user message stores the `model{providerID, modelID, variant}` it was submitted with (L346-351). `session.model` holds the current default. Subagent messages live in the child session with their own assistant `providerID/modelID`; the parent tool part's `metadata.model` records what was requested (`task.ts` L181-189). `/model` switches show up as a different `model` on the next user message and next assistant message; v2 also emits `session.next.model.switched` (`schema/src/session-event.ts` L66) — whether that v2 event fires on the default path is unverified (see Unknowns).

## 6. Human vs harness-authored messages (High for facts, Medium for the inference)

- There is **no** `source`/`origin` field on user messages. TUI (`packages/tui/src/component/prompt/index.tsx` L1094-1110) and `opencode run` (`run.ts` L864) both call the same `session.prompt` with `parts:[{type:"text", text}]`; the resulting rows are indistinguishable by schema. `OPENCODE_CLIENT` (`cli` default, `desktop`, `acp`) is a process env, not stored per message (SRC: `packages/core/src/flag/flag.ts` L75-76).
- Harness-generated user text is marked `synthetic: true` on the **text part**: compaction auto-continue (text "Continue if you have next steps, or stop and ask for clarification if you are unsure how to proceed." with `metadata.compaction_continue: true`; SRC: `packages/opencode/src/session/compaction.ts` L537-542), task summaries ("Summarize the task tool output above and continue with your task.", `prompt.ts` L446-447), shell (`!`) commands ("The following tool was executed by the user", L485), MCP resources (L711+), plan tool. Compaction summaries are assistant messages with `summary: true`. Tool results are `tool` parts on assistant messages, never user messages.
- Therefore: a user message whose text part lacks `synthetic` was submitted by a client over HTTP — human, harness script, or any process on the box. "keep going" typed in the TUI vs sent by `opencode run --session X "keep going"` look identical. Additional distinguishing signal: `POST /session/:id/message` may carry `system` (stored on the user message) — any non-empty `user.system` is an injection vector to flag.
- `session_input.delivery ∈ {steer, queue}` would distinguish mid-turn steering from queued input, but I could not confirm the v2 input path is exercised by the default `SessionPrompt` flow (see Unknowns).

## 8. Launch modes and observability (High)

All local modes run the same server code and the same `opencode.db`:
- **TUI** (`opencode`): spawns a worker that runs `Server.listen` in-process and the UI talks to it via SDK (`cli/tui/worker.ts` L28-58; `packages/tui/src/context/sdk.tsx` L24-25). `opencode attach` / `--port` expose it.
- **`opencode run`**: in-process instance, or `--attach <url>` to a remote server (run.ts L129-134, L346-354).
- **`opencode serve` / `opencode web`**: HTTP server (+ browser UI); web shares sessions with the terminal ([docs/web](https://opencode.ai/docs/web/)).
- **Desktop**: Electron app (`packages/desktop`, electron-builder), spawns a sidecar server via `utilityProcess.fork` on a **random 127.0.0.1 port with a random UUID password**, sets `OPENCODE_CLIENT=desktop`; can instead point at a stored default server URL (SRC: `packages/desktop/src/main/index.ts` L358-388, `server.ts` L45-66). Deepwiki's "Tauri" description is outdated for production ([PR #25822](https://github.com/anomalyco/opencode/pull/25822) consolidated to Electron).
- **VS Code extension**: opens a terminal and runs `opencode --port <port>` (SRC: `sdks/vscode/src/extension.ts` L48-65; [docs/ide](https://opencode.ai/docs/ide/)).
- **ACP** (`opencode acp`, Zed/JetBrains): same server, `OPENCODE_CLIENT=acp` (SRC: `cli/cmd/acp.ts`).
- **Zen / Go**: model gateways, not hosted agents; sessions still run locally ([docs/zen](https://opencode.ai/docs/zen/), [docs/go](https://opencode.ai/docs/go/)).
- **GitHub/GitLab actions**: run in CI runners — off-box, not locally observable ([docs nav](https://opencode.ai/docs/)).

## 9. Tamper surface (High)

- `opencode.db` is a plain WAL SQLite file owned by the user; `opencode db "<sql>"` is a first-class CLI. `message`/`part` rows are upserted from DB on every read (no in-memory cache; `session.ts` pages from `MessageV2.page`), so an edit is immediately "real" to the server. `/undo` deletes rows legitimately; `opencode import` inserts arbitrary sessions.
- Mitigation inherent in the design: the `event` table is append-only with a per-session gap-free `seq` and a uniqueness check on `(aggregate_id, seq)` (event.ts L303-315, L336-348). Deleting/editing a `message`/`part` row does not rewrite `event` rows; a tracker comparing the two exposes tampering. There is no signing, hashing, or integrity mechanism.
- Config/plugins can be swapped mid-run via instance dispose/reload (§2), and `--attach`/`POST /session/:id/message` lets any local process inject a user message with optional `system`.

## Recommended capture design

1. **Organizer-installed plugin** (global `~/.config/opencode/plugins/tracker.ts`, plus `plugin` entry in a managed config) that: (a) on `experimental.chat.system.transform` + `experimental.chat.messages.transform` hashes and archives the exact system array and message list per request (the only lossless view of model input); (b) on `event` appends every event JSON to an external append-only log with local timestamps; (c) on `chat.params` records `model.providerID/modelID`. High confidence this is feasible; all hooks exist.
2. **Independent SSE tailer** (separate process, `opencode serve`-style or attaching to the TUI's `--port`) consuming `GET /event` and `GET /global/event`, writing raw lines; it survives plugin removal and gives a second copy. Ask participants to launch with a fixed `--port` and `OPENCODE_SERVER_PASSWORD` the tracker knows.
3. **Post-run extraction**: dump `event`, `message`, `part`, `session` (incl. `parent_id`), `tool-output/` files, and `POST /sync/history` output; cross-check `part.data` against the last `message.part.updated` event per part and verify `seq` contiguity.
4. **Injection detection**: flag any user message whose text part lacks `synthetic: true` and is not the initial prompt or exactly "keep going"; flag any `user.system`; flag `session.next.prompt.admitted` with `delivery: "steer"` if present; flag instance dispose/reload events and `plugin.added`.
5. **Optional**: `experimental.openTelemetry: true` + local OTLP collector for AI SDK spans as a third, provider-level record (spans contain prompt text; Medium).

## Unobservable modes

- GitHub/GitLab action runs (CI runner) — off-box (High).
- Desktop app pointed at a **remote** default server URL, or `opencode run --attach` to a remote server — storage lives on that remote host (High).
- Any run with the participant's own plugin dir removed/`pure` mode, or after an instance reload with the tracker plugin deleted, unless the SSE tailer is running (Medium).
- Provider request bytes when neither OTEL nor the transform hooks are active (High).

- Whether `tool.execute.after` receives pre- or post-truncation output (Low).
- Whether AI SDK OTEL spans record full inputs/outputs by default in the vendored `ai` version (Medium; PR #5245 discussion says they do).
- Exact caller of `EventV2.remove(aggregateID)` (event-log deletion) (Medium: presumably session delete).
