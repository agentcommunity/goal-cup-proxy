## Deviations, stated rather than buried

1. **`[event]` and `[receipt_binding]` were added to the installed `daemon.toml` by hand.**
   `install-assisted.sh` writes neither (`install-assisted.sh:279-288`). Without them the daemon
   takes the legacy path and criterion 4b measures nothing. Step 6(d) fixes the installer.
   `daemon.toml.as-installed` and `daemon.toml.v4` are both filed here.
2. **Journey A's signed window was 300s, not the runbook's 180s.** The model switch below needed
   headroom; a slow round-trip inside a 180s window would have wasted a journey of quota. Still
   a short signed deadline, and the deadline fired on schedule.
3. **Both journeys switched model to `gpt-5.6-luna` via `/model` before the goal.** The owner
   asked for luna. The pin they had in mind lives in `harnesses/home/codex/config.toml`, which a
   journey never reads: the launch mints a fresh per-entry `CODEX_HOME` seeded only with
   `auth.json` and the connector's own `config.toml`, and that file sets no model. The account
   default was `gpt-6-astra`. The switch is chained as a `<model_switch>` developer record and is
   excluded from the human rule by `manifest.toml:342`, so it cannot affect V2; V5 reports
   **"one model throughout: gpt-5.6-luna"** on both runs.
4. **The bundle's internal `version` label reads `1.0.0`, but the tag is `v0.1.0`.** The bundle
   was staged before the version was settled, with `--version 1.0.0` passed to
   `package-release.py`, and **both journeys ran through that exact installed bundle**. Re-staging
   it now to relabel it would mean the journeys no longer ran against the tagged artifact, which
   is precisely the binding criterion 6 forbids breaking — so the label is left alone and stated
   here instead. The binding that carries weight is `bundle.json`'s `revision`, which is the pin
   and is correct. Re-label at the next staging.

5. **No `/usage` "before" row.** The owner said to proceed rather than supplying the figure, so
   this criterion-6 input has no source. The only quota observation available is the harness's
   own banner, seen on both launches: *"You have 1 usage limit reset available. Run /usage to use
   one."*

## One product finding, not blocking

**Corrected 2026-09-21, after review.** The observation below stands. The *mechanism* first
recorded with it was wrong, and the correct one is narrower and worse-behaved.

**What is observed:** both journeys' **sealed** status documents report `round dates: not
configured (fallback)` with the entry's own timeline, although the daemon was running against a
config whose `[event]` block sets `t0 = 2026-09-17T00:00:00Z`.

**What was first written, and is wrong:** that the value is "lost between `config.event` and
`StatusPayload`". It is not. The live path is correct end to end — `config.rs:112` parses it,
both `EntryRuntime` constructors (`control/handlers.rs:1326`, `runtime/daemon.rs:1036`) set it,
and `status.rs:254`/`:284` compose and classify it correctly.

**What actually happens:** `compose_capture_closed` (`status.rs:304`) is a *second, independent*
payload builder used only for capture-closed rows. Its signature is `(entry: &Entry, now: f64)` —
it has no config and no runtime — so at `status.rs:345` it hardcodes
`event: fallback_event_status(entry)`. `publish_capture_closed` (`status.rs:378`) then overwrites
the cache, the mirror and the status line with that document. **The round is correct for the
whole run and is clobbered at the seal.**

**The observation that settled this was made on a live artifact that no longer exists, and
that is stated rather than glossed.** Journey B's status taken *while live* carried **no**
round-dates line, while the same entry's status after sealing carried it — one entry, both
states, opposite answers. That line prints only under `Fallback` (`commands/status.rs:349`), so
its absence said the live document was correctly `Config`.

`statusB-interrupted.out` was never copied into this bundle and its source directory has since
been deleted, so **that artifact is gone and the observation is not reproducible from this
repository.** What survives is stronger anyway, because it does not depend on an artifact: the
defect is readable in the source (`status.rs:345` hardcodes the fallback in a builder that has
no config), and the falsification test in
`docs/superpowers/plans/2026-09-21-step6-findings.md` item 4 re-derives the behaviour from a
fresh run in two commands. Treat the lost file as corroboration that was, not as evidence that
is.

**Why the unit test did not catch it:** `tests/event_status.rs` asserts
`EventStatusSource::Config` and passes, but every one of its cases reads the cache while the
entry is still open. No test in the workspace asserts `event_status_source` on a capture-closed
entry. The unit under test is the live composer; the unit that ran here is the terminal one.

**Still not affecting the claim.** V13 checks the receipt-and-deadline binding and passes on both
runs; `[receipt_binding]` took effect in full. But `docs/archive/v1/JOURNEY-RUNBOOK.md` §4b remains **wrong
to present that line as the tell for the legacy path** — here it appears on two runs that took
the workspace-submission path completely, and an operator following the runbook would have
discarded the first two journeys ever to measure criterion 4b.

The fix is not one line: `Entry` (`registry.rs:1274-1351`) carries no event field, and the
runtime that held it is evicted at seal. Options and a decisive falsification test are in
`docs/superpowers/plans/2026-09-21-step6-findings.md` item 4.
