## Headline, for the owner

**1. The assertion that has never run on any machine in this repository's history PASSED.**
`a_tui_launch_with_no_process_group_uses_the_descendant_walk`'s `else` arm asserts
`all_gone && !harness_unverified`. On Linux it is true. `pidfd_open` + `pidfd_send_signal` give
the instance-bound delivery the `Anchor` split was written for, and **`all_gone: true` is
reachable on Linux**. That is the thing macOS structurally cannot do, and it works.

**2. The daemon cannot capture a submission on Linux at all — and this is the biggest finding.**
`promote_child_exclusive` and `promote_child_dir_exclusive` in
`crates/goalcup-platform/src/tracecap/unix.rs` are implemented **only** for macOS, via
`renameatx_np(..., RENAME_EXCL)`. The `#[cfg(not(target_os = "macos"))]` arm at `:474-481` and
`:584-591` is a stub that unconditionally returns `Refused(UnsupportedFileSystem)`.
`submission.rs` maps that to `SubmissionFailureV1::StorageFailed`. Linux has the exact
equivalent, `renameat2(RENAME_NOREPLACE)`, and it is simply not written. **This is the root cause
of 39 of the 60 test failures below** (§7). Thirty were counted from panic text on
2026-09-16; nine more were attributed on 2026-09-17, after the stub was implemented, and
confirmed by simulating the stub on macOS (see the correction in §7).

**Not "nothing works on Linux", and the report is careful about this.** §3 records that the
CLI-driven end-to-end path — a real `goalcup start`, a real harness, a real `goalcup seal`,
verified — **passes on Linux** and never touches this stub. So the outage is the exclusive-promote
capture path, not capture in general. This lane did not establish what separates the two, and the
owner should not read it as either wider or narrower than that.

**3. The other never-run assertion FAILED, and the test is wrong, not the implementation.**
`a_child_started_before_the_next_authenticated_snapshot_is_chased:440` asserts `r.all_gone`. Its
handle comes from `support::handle`, which sets `pgid: Some(pid)`, and `terminate.rs:347` sets
`atomically_bound = group.is_none()`. A group-leading handle therefore makes `all_gone` false on
**every** platform, by design. Measured proof is in §6.1: the same fixture with `pgid: None`
reports `all_gone: true`. The kill itself worked in both shapes. The one-line owner fix is
`h.pgid = None`, which is exactly what the two sibling tests do. **It was not applied.**

**4. A fixture is vacuous on Linux and its own guard caught it.**
`wrapper-setpgid-grandchild.sh` relies on `set -m` to put a background job in a new process
group. `/bin/sh` here is **dash**, which turns job control off without a controlling tty, so the
helper never leaves the launch's group. The test's vacuity guard at `:157` fires correctly. The
walk-versus-group-escape property — which Lane Q0 measured as carrying the whole containment
guarantee on the real harness — is therefore **unproven on Linux**.

**5. The gate is red at step 3, before it ever reaches the tests.** `cargo clippy` fails on three
lints. Two are genuinely Linux-only. Lane B's CI will go red on clippy unless this is handled.

**6. This container runs as uid 0 with full capabilities, which voids every permission-refusal
test.** Seven failures are artifacts of that and not Linux findings at all. §5 separates them by
measurement, not by guesswork.

```
panicked at crates/goalcup-daemon/tests/process_kill.rs:440:9:
```

The assertion prints only `still_alive`, so I rebuilt the test's exact handle shape in a
throwaway probe (scratchpad only, never committed, no repo file touched) to read the struct the
test does not print. Both runs use the same fixture, `wrapper-late-fork.sh`:

```
=== pgid = Some(9801) ===   <-- EXACTLY what the failing test builds
TerminationReport {

    guard_degraded: true,
    harness_unverified: false,
}
forked_newcomer=Some(9864) still_alive=Some(false)
```

**Judgement: the test's Linux expectation is wrong. The implementation is right.** The evidence:

1. The kill **worked**, in both shapes. The late-forked newcomer was chased and is dead
   (`still_alive=Some(false)`), which is the property the test was written to pin, and the test
   still asserts it at `:442` where it would have passed.
2. `still_alive: []` and `observed_gone: true` — nothing survived.
3. `all_gone` is false for one reason only: the handle leads a process group. The test calls
   `support::handle(...)` at `:424`, which sets `pgid: Some(pid)` (`process_kill.rs:910`), and the
   fixture is spawned into its own group. `terminate.rs:347` is `let mut atomically_bound =
   group.is_none();` — a numeric `killpg` is never instance-bound, **on any platform, by design**.
   So this `else` arm is unsatisfiable by construction; it is not a Linux question at all.
4. The control proves it: flip `pgid` to `None` and the same fixture reports `all_gone: true`.
5. The sibling that sets `h.pgid = None` and *does* assert `all_gone` on Linux is
   `a_tui_launch_with_no_process_group_uses_the_descendant_walk` (`:104`, `:110`). Two further
   siblings (`:227`, `:276`) set `h.pgid = None` with a comment naming this exact reason, though
   they assert on `observed_gone`/`harness_unverified` rather than `all_gone`. This one set
   nothing.

**Three further checks, done independently after the measurement above, all agree.**

6. **The codebase already states the rule as a test.** `a_launch_that_leads_its_own_group_is_killed_as_a_group`
   (`:300-324`) asserts `h.pgid == Some(child.pid)` — "the fixture is spawned into its own process
   group" — and then asserts `!r.all_gone` at `:318`. That is this repository's own explicit,
   passing statement that **a group-leading handle must never report `all_gone: true`.** The
   failing test asks for the opposite from the same kind of handle.
7. **The determinism is structural, not probabilistic.** `atomically_bound` is declared exactly
   once, at `terminate.rs:347`, and the only four later writes (`:375`, `:433`, `:468`,
   `:521`) are `&=`. It is monotonic: once false it cannot become true. So for a group-leading
   handle `all_gone` is false before the first SIGTERM is sent — no ordering, no pidfd outcome
   and no machine load can change it. This failure would reproduce on any Linux machine.
8. **The Linux arm predates the commit that made it unsatisfiable.** `git blame` puts
   `assert!(r.all_gone, ...)` at `:440` in `a9cf96d` (2026-09-11). Four days later `4d15fbb`
   edited *this very `if`* — `:438`, the macOS arm, is that commit's — and left the Linux arm
   beside it untouched. Nothing compiled it, so nothing asked.

The owner's fix is one line — `h.pgid = None` at `:424`, matching its siblings. **Lane A did not
apply it.** The judgement above should be checked by someone who did not measure it.

For the record, one hypothesis was **refuted** on the way here: that `Anchor::Closed`'s
`Err((!is_alive(pid)).then_some(false))` (`terminate.rs:1175`) was clearing `atomically_bound`.
That path is real and could clear the flag for a `pgid: None` handle in a narrow window, but it
is moot in this test — the flag is already permanently false from `group.is_some()` at `:347`
before any member is signalled. The failure has nothing to do with the `Anchor` split.

### 6.2 `a_grandchild_in_its_own_process_group_is_still_named_by_the_descendant_walk:157` — *fixture portability, neither implementation nor expectation*

```
panicked at crates/goalcup-daemon/tests/process_kill.rs:157:5:
assertion `left != right` failed: the helper must have left the launch's process group
                                 or this fixture is vacuous
  left: 30347
 right: 30347
```

`terminate()` is never reached, so there is no report struct to print. The panic is the test's own
vacuity guard.

`wrapper-setpgid-grandchild.sh` says in its own comment: "`set -m` is how POSIX sh makes the same
syscall: with job control enabled, each background job is started in a new process group." That is
true of **bash**, which is macOS's `/bin/sh`. It is not true of **dash**, which is this Linux's
`/bin/sh`. Direct probe:

```
$ /bin/dash -c 'set -m; sleep 5 & ps -o pid,pgid -p $!; echo self=$(ps -o pgid= -p $$)'
/bin/dash: 1: set: can't access tty; job control turned off
  PID  PGID
31350 31348          <-- same pgid as the shell
self=31348

$ bash -c 'set -m; sleep 5 & ps -o pid,pgid -p $!; echo self=$(ps -o pgid= -p $$)'
  PID  PGID
31499 31499          <-- its own pgid
self=31497
```

Under `cargo test` there is no controlling tty, so dash refuses job control and the helper stays
in the launch's group. **The fixture proves nothing on Linux, and it says so rather than passing
quietly** — the guard is doing its job and should stay.

**What this costs.** Lane Q0 measured on a live Codex session that almost everything the agent
starts leaves the launch's process group, so the descendant walk carries the whole termination
guarantee. That is precisely the property this fixture exists to pin, and **it is unmeasured on
Linux.** A termination that had quietly become group-only would pass every other fixture in the
file.

## 7. The largest finding: the daemon cannot promote a submission on Linux

`crates/goalcup-platform/src/tracecap/unix.rs`:

```rust
        #[cfg(target_os = "macos")]
        { ... libc::renameatx_np(..., libc::RENAME_EXCL) ... }      // :410-472

        #[cfg(not(target_os = "macos"))]
        {
            let _ = (staged, final_name);
            Err(TraceCapError::refused(
                "promote exclusive trace child",
                RefusalKind::UnsupportedFileSystem,
            ))
        }                                                            // :474-481
```

The identical pattern repeats at `:507-590`, which is the body of `promote_child_dir_with_expected` (`promote_child_dir_exclusive` at `:484-490` is a pass-through into it). On Linux both are
**unconditional refusals**. `submission.rs` maps the resulting refusal to
`SubmissionFailureV1::StorageFailed` on the paths capture actually reaches first — `:340` (sealing
source), `:425` (capture journal) and `:1161` (object store). The submission-directory promote at
`:805` would instead surface `RecoveryAmbiguous`.

Measured consequence, counted from the panic text of each failing test rather than estimated:
`StorageFailed` or `UnsupportedFileSystem` is the panic value for 8 of the 10 tests in the
`submission::tests::*` group — every one that reaches `capture_submission`, all of
`submission_snapshot` (**18 of 18**), and — as corrected on 2026-09-17 — **all 13**
`finalization_recovery` failures. Four name `StorageFailed` in their panic text
(`admission_samples_time_inside_the_cas…`, `control_finish_replays_terminal_and_dual_oow_marker…`,
`observed_deadline_survives_clock_rollback…`,
`v4_attach_is_refused_before_writing_a_zero_generation_workspace`); the other nine do not, for the
reason given below.

**Corrected 2026-09-17: the other 9 ARE this stub**, by a different route than the 30. Not the
directory promote at `submission.rs:805`, which this platform never reaches, but
`promote_child_exclusive` via `install_sealing_source_once` (`tracecap.rs:921-923`) from
`prepare_source_journal` (`entry.rs:2835`, `submission.rs:317/340`). That makes every live
`finish_entry` fail *before* the intent CAS, so no `sealing_intent` is ever written and each test
dies later reading a null.

This report's discriminator produced false negatives. It sorted the 13 by whether `StorageFailed`
appeared in the panic text, but seven of the nine assert only
`assert!(daemon.finish_entry(…).is_err())` — which this failure satisfies **for the wrong reason**
— and then discard the error. The absence of `StorageFailed` was an artifact of assertion shape,
not evidence of a different cause. Those assertions should test the error's shape, not merely that
one occurred.

Confirmed by experiment rather than left as a source reading: on macOS, forcing
`rename_exclusive` to return `Refused(UnsupportedFileSystem)` behind a temporary flag reproduces
**3 passed / 13 failed** against a 16/16 baseline, and the 13 are exactly these names. The
experiment ran on 2026-09-17 against `v1/trunk`; the patch was reverted in the same command and is
not in the tree. This is a macOS simulation of the Linux stub, not a Linux measurement — a CI run
at `v1/trunk` remains the definitive check, and any residue there is new information.

**Judgement: the Linux implementation is missing, not wrong.** Linux has had
`renameat2(RENAME_NOREPLACE)` since 3.15 and it is the exact semantic equivalent of
`renameatx_np(RENAME_EXCL)`. Nobody wrote it, and with no CI nothing ever asked. This is a
V1.1-scope gap (V1 is the macOS foundation per the 2026-09-13 spec) but it is worth the owner

## 8. `finish_matrix` — a latent test defect that Linux timing exposes

Two of three tests fail, 3/3 reruns, single-threaded:

```
panicked at crates/goalcup-cli/tests/finish_matrix.rs:106:6:
the harness stand-in registers at its initial generation: Busy("the daemon is busy with this
entry: entry eb22e938ea7b64fe4 is mid-upload: its runtime is out of the map for the length of
one pump, and this call would have to hold a lock across it")
```

`finish_matrix.rs:97` and `:191` wrap the `/process` registration in `retry_busy` — 3 attempts,
200 ms apart. But `crates/goalcup-cli/src/retry.rs:8-13` explicitly carves `/process` out of that
generic helper, and every production caller uses the dedicated
`retry_busy_process_classified` — 9 attempts on a dephased schedule totalling ~12 s
(`commands/start.rs:691`, `commands/resume.rs:781`, `commands/resume.rs:1362`). The daemon's own suites treat meeting a
busy runtime mid-pump as expected scheduling, not a defect
(`entry_lifecycle.rs:3094-3105`). With `upload_interval_ms = 200` in this test's config, the
generic helper's ~400 ms of total backoff is the same order as the pump cadence.

**Judgement: a test defect, not a Linux defect, and not really a platform expectation either.**
The test uses the wrong retry policy for the route. It passes on macOS by timing luck. I could
not verify that swapping to `retry_busy_process_classified` fixes it, because that is a source
change this lane does not make.
