# Fix plan v3, local test day 2026-10-22 (after the 120-minute cells)

After [v1](2026-10-22-fix-plan.md) and [v2](2026-10-22-fix-plan-v2.md). Six 120-minute staging
practice cells ran 18:21-20:31Z (Hermes, Amp and Codex on the Mac host and in Docker; network cut,
pause and disk-pause drills; subagent workloads). Every run reached its deadline, sealed and
uploaded; memory and open files stayed flat; the network cut recovered (the ACK covered the
pre-cut tail 9.4 minutes after the cut ended). Every matrix row still said FAIL, and the pass lines
could not judge the drills. The product held; the kit and two status lines did not.

## What the long cells showed, together

The kit was written for 10-minute runs and measures a long run with 10-minute assumptions:

- After about 30 minutes the CLI prunes acknowledged chain parts locally (by design), so a long
  run's trace holds only the last part. `scripts/matrix.sh` (~line 1027) requires `chain.jsonl`
  and FAILs before verifying anything ("no chain.jsonl in the trace"). The local verifier then says
  `chain_pruned_locally` and points to the server copy, which the kit never fetches.
- Uploads are a 30-minute timer by design (`crates/goalcup-cli/src/upload/policy.rs` ~80-83: first
  wait random, early at 256 MiB, all at the end). LOCAL-CAMPAIGN's pass line "ACK lag back under 2
  minutes within 25 minutes after a cut" and `scripts/campaign.py` `ack_recovered` (~944,
  `ACK_RECOVERY_WINDOW_S` ~94, testing `ack_age_s <= 120`) cannot hold for that cadence.
- `goalcup status` says "Upload: up to date (last sent 16 min ago)" while thousands of records
  wait for the next timed send (`crates/goalcup-cli/src/commands/status.rs` ~367 `UpToDate` means
  "worked once, no current error"; `participant/status.rs` ~165-166), and its capture line always
  says "delivery local_only, anchor local_only" (a daemon constant, `crates/goalcup-daemon/src/
  runtime/capture/mod.rs` ~1288; the daemon never knows uploads, D3).
- The workloads end in about 5 minutes with cheap models, so a 2-hour cell is 115 minutes idle and
  a network cut on an idle chain proves little.

## Items

### L1. The matrix verifies a long run's server copy
- In `scripts/matrix.sh`, when the trace has no `chain.jsonl` but has `chain.<offset>.jsonl`
  parts (pruned), rebuild the server copy with `scripts/fetch-run.sh` (index from the database read
  only, objects from R2 with a read-only token, both from files or env the operator gives; or skip
  with a clear `NOT VERIFIED: long run, server copy not fetched` line, never a FAIL of the run) and
  run the same verify, server-copy and model checks on it, plus a check that the local tail part
  equals the server copy's tail bytes.
- Tests with a fake pruned trace and a fake fetch (test_matrix.py).

### L2. Pass lines that match the 30-minute upload cadence
- LOCAL-CAMPAIGN "Pass lines": "after a cut or pause ends, an acknowledgement covering the last
  record written before its end arrives within 35 minutes" (30-minute timer plus margin).
- `scripts/campaign.py`: `ack_recovered` passes when `acked_seq >= chain_last_seq` at the drill's
  end within `ACK_RECOVERY_WINDOW_S = 35 * 60`; samples every 5 minutes are enough for that.
  Tests with the fake clock and synthetic samples.

### L3. `goalcup status` says what is true about the upload
- "Upload: working, sent every 30 minutes (last sent N min ago; M records wait for the next send)"
  instead of "up to date" when records wait; "up to date" only when acknowledged equals written.
  Hide or reword the daemon's constant "delivery local_only, anchor local_only" in the participant
  view (it is about the local anchor, not the upload). Test the wording cases
  (`crates/goalcup-cli/src/participant/tests.rs` ~305).

### L4. A workload that lasts hours
- `docs/research/campaign-long-workload.txt`: the many-step task plus "after step 15, take the
  next item from TODO.md and keep going until the deadline; add new TODO items as you find them",
  and `goalcup time-left` every hour into TIME.md. LOCAL-CAMPAIGN points long cells at it.

### L5. The research report attributes subagents (verifier decoders)
The server copies of all six long runs verify (valid, signed, 0 gaps) and hold every subagent's
traffic, but the research report does not say which messages are a subagent's:
- Amp: subagents share the parent's thread WebSocket; every subagent event carries
  `parentToolUseId`/`parentToolCallId`. The decoder (`crates/goalcup-verifier/src/
  capture_analysis/thread.rs`) files them under the parent without that field, and `Task` tool
  results are `unsupported_tool_result`. Carry the parent id; decode `Task` results. No follower is
  needed for coverage (update docs/research/AMP-FOLLOWER.md).
- Codex native: `response_item.message` and `event_msg.item_completed` are unrecognised and
  `spawn_agent` is not decoded as a tool call (`capture_analysis/native/codex.rs`).
- Hermes: `delegate_task` children appear only on the wire, unattributed; say so in
  docs/harnesses/hermes-cli.md until the native `session_*.json` decoder exists.
- Tests from redacted fixtures (spikes/redact.py, reviewed by eye) of today's runs.
