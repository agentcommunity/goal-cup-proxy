# Fix plan v10, 2026-10-22 (a client that closes before its TLS greeting is not a loss)

Round 2's mac-amp run (rbb34eb43a003abbd) verified `incomplete` with 2 gaps: both `decode_failed`,
no stream, no host. Seq 30151 at 02:47:55.425Z was written by the recording proxy 56 ms before a new,
normally intercepted connection to ampcode.com; seq 35614 is the daemon repeating the proxy's
fail-open count at the seal. The proxy line read `fail_open=2 failed=6 client_tls=5`. Every other
round-2 run verified valid with 0 gaps.

## Cause (inferred from the code; the proxy does not record why it tunnelled)
- After the proxy answers `200` to a CONNECT for an approved host, a client that closes before
  sending any bytes makes `peek_client_hello` return `NeedMore` (`crates/goalcup-cli/src/proxy/
  connect.rs` ~1019). That becomes `ClientHelloUnparsed` (~552), and the proxy opens an empty
  pass-through and counts `fail_open` (`proxy/mod.rs` ~943), which becomes a loss gap
  (`api.rs` ~49). No byte reached the model host, so nothing was lost. Amp drops connections
  routinely (every Amp run shows `client_tls` failures).

## Item U1 (product)
- A client that closes (EOF) before sending a complete ClientHello is a client failure (`ClientIo`):
  no upstream connection, no `fail_open`, no loss gap. A ClientHello that arrives but cannot be
  parsed, has no SNI or names another host stays fail-open as today.
- `proxy admission:` breaks `fail_open` down by reason (unparsed, no_sni, sni_mismatch, not_tls), so
  the next one is diagnosable from host.log.
- Tests: CONNECT to an approved host, close right after the `200` -> `fail_open=0`, no gap, a client
  failure counted; a client that sends garbage -> still fail-open with its reason.
